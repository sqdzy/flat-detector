# Spec: flat-detector — мониторинг ближних Химок и Telegram-подписки

**Author:** проектная спецификация ChatGPT для sqdzy  
**Date:** 2026-09-23  
**Status:** Draft / требуется утверждение владельца и проверка разрешений источников  
**Reviewers:** владелец проекта; разработчик бота; разработчик источников; QA/security review  
**Related:** [Архитектура](ARCHITECTURE.md), [источники и риски](SOURCE_POLICY.md), [тест-план](TEST_PLAN.md), [MCP contract](../mcp/tools-manifest.json)

## Context

Нужен собственный автономный сервис для отслеживания **однокомнатных квартир на продажу в ближних Химках** с доставкой проверенных актуальных вариантов через Telegram всем, кто сам подписался на бота. Предыдущий ручной/ChatGPT мониторинг неоднократно находил объявления, уже снятые с публикации, и слишком удалённые от Москвы. Сервис должен явно хранить доказательства актуальности, исключать снятые объявления, различать непроверенные и подтверждённые и учитывать реальную доступность МЦД-3.

Начальная геозона — вручную утверждённые полигоны около МЦД-3 **Левобережная** и **Химки** (приоритет первых доступных станций ближе к Москве). Сходня, Фирсановская, Подрезково, Новоподрезково и удалённые районы по умолчанию исключены. Пешая доступность или короткая поездка до этих станций — целевой показатель, ориентир 10–15 минут; время должно сопровождаться методом измерения и оценкой достоверности. Универсальное правило «формально Химки = подходит» недопустимо.

Приоритетная цена до **8,5 млн ₽**, диапазон **8,5–9,0 млн ₽** — отдельная категория при доказуемых преимуществах, свыше 9,0 млн ₽ не подходит. Подписчики могут уменьшать собственный лимит, но не увеличивать проектный жёсткий предел без явной политики администратора. Время ежедневного дайджеста владельца — **11:00 Europe/Berlin**, с корректным переходом на летнее/зимнее время. Новые пользователи по умолчанию выбирают собственную временную зону или подтверждают отображаемую.

Технический фундамент — новый пустой репозиторий. Проектируем документацию до кода. Неизвестные коммерческие/юридические разрешения по источникам **не считаются полученными**. Система должна быть полезной на разрешённых данных и synthetic fixtures, не обещать работу заблокированных площадок и не пытаться обходить их защиту.

## Scope and assumptions

- MVP: персональные приватные Telegram-уведомления, добровольная подписка, общий набор проверенных объявлений и персональные пороги, read-only MCP для ChatGPT.
- Владелец позже утверждает фактические полигоны ближних Химок и первого законно автоматизируемого источника.
- В будущем можно добавить Mini App, карту, несколько городов, многокритериальные фильтры и отдельный LLM evaluator; это не блокирует MVP.
- ChatGPT в обычном чате работает по запросу через MCP; постоянная обработка, очередь и Telegram-рассылка всегда серверные, а не внутри чата.
- Точность объявления гарантировать невозможно: открытые данные лишь признаки, для сделки требуется собственная проверка документов и непосредственное подтверждение у продавца.

## Functional Requirements

- FR-1: Система **MUST** хранить `Source Registry` с разрешёнными режимами получения данных, подтверждением прав/условий использования и датой последней проверки каждой площадки.
- FR-2: Система **MUST NOT** автоматически обращаться к площадке с состоянием `DISABLED`/`UNKNOWN_PERMISSION` или без подтверждённого разрешённого режима.
- FR-3: Система **MUST** иметь интерфейс `SourceAdapter` для лицензированного API, согласованного фида, разрешённого HTML и ручного/разрешённого импорта с единым выходным форматом.
- FR-4: Система **MUST** ставить автоматические проверки только в очередь с ограничением скорости на источник, тайм-аутами и отключением на политическую/техническую блокировку; не обходить CAPTCHA, 403, robots/оговорённые ограничения.
- FR-5: Система **MUST** отражать на 401/403/429/CAPTCHA статус `SOURCE_BLOCKED`/`RATE_LIMITED` и не подменять эти ошибки пустой выдачей или `REMOVED`.
- FR-6: Система **MUST** нормализовать извлечённые поля (ссылка, ID, цена RUB, площадь, комнаты, этаж, адрес, состояние, время наблюдения) с явными `unknown` и provenance по каждому полю.
- FR-7: Система **MUST** устранять повторы одного внешнего ID и консервативно связывать дубли между площадками; сомнительные связи **MUST** оставаться на ручную проверку.
- FR-8: Система **MUST** вести историю цены, времени наблюдения и существенных изменений, различая обычную перепубликацию от содержательного обновления.
- FR-9: Система **MUST** разделять `ACTIVE_DIRECT`, `ACTIVE_INDIRECT`, `UNVERIFIED`, `STALE`, `RESERVED`, `REMOVED` и `SOLD` с подтверждающими evidence и временем наблюдения.
- FR-10: Дайджест **MUST NOT** рекомендовать `REMOVED`, `SOLD`, `RESERVED`, `UNVERIFIED`, `STALE` как доступные для звонка. `ACTIVE_INDIRECT` **MUST** маркироваться как косвенная проверка.
- FR-11: Базовый поисковый профиль **MUST** ограничивать тип недвижимости «однокомнатная квартира», целевые вручную заданные полигоны и исключённые дальние районы; геонеоднозначность отправлять на проверку.
- FR-12: Ранжирование **MUST** отдавать приоритет цене ≤8 500 000 ₽; диапазон (8 500 000, 9 000 000] ₽ **MUST** попадать в отдельную категорию с подтверждённой причиной преимущества; >9 000 000 ₽ **MUST** исключаться.
- FR-13: Для публикуемого объявления сервис **MUST** показывать ориентир расстояния/времени до Левобережной или Химок и тип маршрута, а при недоступном маршрутизаторе явно обозначать отсутствие подтверждения.
- FR-14: Система **SHOULD** собирать только публичные/разрешённые признаки несоответствий (цена относительно аналогов, противоречие текст/фото при разрешении, подозрительные перепубликации), без бездоказательных обвинений продавца.
- FR-15: Каждая рекомендация **MUST** содержать ссылку на оригинал, источник, наблюдённые цену/площадь/адрес, статус, время актуализации и объяснимые плюсы/риски.
- FR-16: Telegram-бот **MUST** регистрировать подписку только после явного взаимодействия пользователя с ботом и подтверждения подписки; самопроизвольная рассылка неизвестным `chat_id` запрещена.
- FR-17: Telegram-бот **MUST** предоставлять интерфейсы `/start`, `/help`, `/settings`, `/stop`, `/delete_me` и кнопку настройки бюджета, геозоны (в рамках разрешённого) и режима уведомления.
- FR-18: Scheduler **MUST** формировать ежедневный дайджест для владельца в 11:00 `Europe/Berlin`, соблюдая DST; для остальных пользователей — сохранённую временную зону и локальный час рассылки.
- FR-19: Доставка **MUST** использовать устойчивую transactional outbox и ключ dedup на событие/подписчика/версию; корректно обрабатывать 429 `retry_after`, 403 bot blocked и неопределённый результат сетевого тайм-аута.
- FR-20: `/stop` **MUST** прекращать будущие доставки без задержки в планировщике; `/delete_me` **MUST** удалять профиль пользователя и минимизировать необязательные связанные идентификаторы с учётом действующей retention policy.
- FR-21: MCP **MUST** предоставлять ограниченные read-only инструменты просмотра сохранённых объявлений, доказательств, состояния источников и предварительного дайджеста без сетевого сбора или отправки сообщений.
- FR-22: Административный MCP **MAY** ставить строго ограниченную перепроверку существующего `listing_id` в очередь только роли owner с явным `confirmed=true` и запретом arbitrary URL.
- FR-23: Система **MUST** хранить происхождение каждого опубликованного факта и метку `permission_scope`, не ретранслировать фотографии/массовые тексты без отдельного лицензионного разрешения.
- FR-24: Система **MUST** предоставлять приватные owner-only журналы задач, блокировок, причин исключения, сигналов о деградации источников и агрегированные метрики без раскрытия секретов/телефонов продавцов.

## Non-Functional Requirements

- NFR-1 [Legal]: до включения адаптера **MUST** быть зафиксированы юридическое основание и фактически доступный разрешённый канал; отсутствие согласования блокирует адаптер.
- NFR-2 [Security]: **MUST** использовать domain/path allowlist + DNS/IP/redirect валидацию; 100% известных SSRF-тестов в TEST_PLAN **MUST** отклоняться до network I/O.
- NFR-3 [Security]: секреты Telegram/MCP/API **MUST** храниться вне исходного кода и model-visible аргументов; в логах/ответах должно быть 0 исходных секретов.
- NFR-4 [Isolation]: collector **MUST** работать non-root, без docker.sock и без Telegram токена; MCP read-only роль **MUST NOT** иметь доступ к изменению подписок/рассылке.
- NFR-5 [Reliability]: успешно зафиксированные нормализованные наблюдения **MUST** переживать перезапуск контейнеров и повторный запуск задания без потери history; гарантия ровно одной физической доставки Telegram **не обещается** из-за неопределённого исхода тайм-аута API.
- NFR-6 [Idempotency]: для известных успешных ответов Telegram должно быть 0 повторных отправок при повторе scheduler/restart; статус неопределённой отправки выделен отдельно.
- NFR-7 [Delivery]: 95% сформированных дайджестов **SHOULD** передаваться в Telegram ≤10 минут от заданного времени при доступности Telegram и базы; показатель подтверждается пилотом.
- NFR-8 [Freshness]: публикация в категории «подтверждено актуально» **MUST** содержать положительный сигнал не старше 24 часов (настройка может ужесточаться по площадке).
- NFR-9 [Latency]: read-only MCP при 1000 записей и p95 локальных запросов **SHOULD** отвечать ≤2 секунд без внешнего сетевого обращения; измеряется integration benchmark.
- NFR-10 [Capacity]: MVP **MUST** выдерживать не менее 100 подписчиков, до 1000 нормализованных карточек и одновременное исполнение двух разрешённых сборщиков без потери Telegram webhook обновлений.
- NFR-11 [Observability]: 100% scan jobs, завершившихся ошибкой, **MUST** иметь структурированный код ошибки и `run_id`; не писать сырой контент/токены в лог по умолчанию.
- NFR-12 [Backups]: ежедневный зашифрованный backup БД и успешный документированный тест восстановления минимум раз за календарный месяц.
- NFR-13 [Privacy]: минимизация Telegram ID, никаких телефонных номеров подписчиков по умолчанию, доступ только по ролям, `/delete_me` завершается ≤24 ч для всех необязательных персональных данных; policy пересмотреть под юрисдикции целевой аудитории.
- NFR-14 [Source safety]: на 403/CAPTCHA немедленная остановка данного режима сбора; повторный запуск только после анализа/исправления разрешённого доступа, не автоматический «обход».
- NFR-15 [Messaging]: глобальная отправка ниже бесплатного Telegram порога с токен-бакетом (начальная настройка 15 сообщений/с и 1 сообщение/с на чат); 429 всегда подчиняется `retry_after`.
- NFR-16 [Time]: планировщик хранит расписания как IANA time zone и UTC timestamps; переход DST не должен создавать два дайджеста в один локальный календарный день.

## Acceptance Criteria

### AC-1: Источник запрещён без доказанного разрешения (FR-1, FR-2, FR-3)
Given площадка имеет `UNKNOWN_PERMISSION` и адаптер поддерживает HTML
When scheduler запускает цикл
Then запросов на домен площадки сделано 0, job получает `SOURCE_NOT_ALLOWED`, а owner видит причину и возможный разрешённый канал.

### AC-2: Лимиты и обнаружение антибот-блокировки (FR-4, FR-5)
Given разрешённый тестовый адаптер имитирует 403/429/CAPTCHA
When collector выполняет проверку
Then он фиксирует `SOURCE_BLOCKED`/`RATE_LIMITED`, останавливает неразрешённые повторы и не помечает объявления удалёнными.

### AC-3: Нормализация и слияние одного объявления (FR-6, FR-7)
Given две разрешённые записи с одинаковым source ID, а затем два похожих, но неоднозначных объявления из разных источников
When worker нормализует пачку
Then source-ID запись единственна, provenance полей сохранён, а межсайтовые неоднозначные записи не сливаются автоматически.

### AC-4: История изменений (FR-8)
Given квартира ранее наблюдалась за 8,4 млн ₽ и сейчас разрешённый источник сообщает 8,1 млн ₽
When проходит повторный scan
Then сохраняется новая запись истории и одно событие `PRICE_DROP` с предыдущей/новой ценами и датами.

### AC-5: Положительная и косвенная актуальность (FR-9, FR-10)
Given одна квартира активна напрямую сейчас, вторая подтверждена двумя независимыми разрешёнными источниками, третья имеет только 403
When формируется shortlist
Then первые две могут попасть с разными прозрачными метками, а третья отправляется на перепроверку и не обозначается активной.

### AC-6: Снятые/забронированные исключены (FR-9, FR-10)
Given у квартиры есть актуальное явное свидетельство `REMOVED` или `RESERVED`
When формируется новый дайджест
Then квартира отсутствует в рекомендованном списке, а статус сохраняется в истории.

### AC-7: Геозона ближних Химок (FR-11)
Given имеются однушки в утверждённых полигонах Левобережной/Химок и похожие квартиры в Сходне/Подрезкове
When применяется базовый профиль
Then дальние адреса отсекаются, а объявления с неоднозначным адресом не включаются автоматически.

### AC-8: Два ценовых диапазона (FR-12)
Given три актуальных варианта по 8,3 млн ₽, 8,8 млн ₽ с обоснованным преимуществом и 9,1 млн ₽
When строится дайджест
Then первая квартира в основном списке, вторая — отдельно как исключение, третья исключена.

### AC-9: Достоверность транспорта (FR-13)
Given для одного объявления доступна лицензированная пешеходная маршрутизация до станции, а для второго маршрутизатор недоступен
When формируется карточка
Then первая содержит время, станцию, режим расчёта и timestamp; во второй отсутствует придуманное число минут, пометка «маршрут не проверен».

### AC-10: Объяснимые риски и источник фактов (FR-14, FR-15, FR-23)
Given цена на 35% ниже медианы проверенных аналогов и отсутствует подтверждение документов
When система создаёт рекомендацию
Then она указывает факт ценового отклонения и необходимость проверить документы, ссылку/время каждого доступного факта и не называет продавца мошенником.

### AC-11: Подписка только с согласия (FR-16, FR-17)
Given пользователь Telegram впервые присылает `/start`
When он подтверждает подписку и параметры
Then создаётся одна активная подписка на его собственный `chat_id`, команды `/help` и `/settings` доступны; без подтверждения scheduled доставки нет.

### AC-12: Часовой пояс и переход DST (FR-18)
Given у владельца установлен Europe/Berlin и дата переключения CEST↔CET
When scheduler доходит до очередного локального дня
Then ровно один дайджест создаётся в 11:00 соответствующего локального смещения; UTC execution timestamps различаются правильно.

### AC-13: Не отправлять известные дубли (FR-19)
Given один и тот же event обработан дважды из-за scheduler restart
When outbox принимает повтор
Then уникальный ключ оставляет единственную запись доставки для subscriber/event/version; ранее подтверждённое Telegram сообщение не отправляется повторно.

### AC-14: Telegram 429 и неопределённая отправка (FR-19)
Given Telegram возвращает `429` с `retry_after=7`, а отдельная тестовая отправка обрывается после записи запроса в сокет
When delivery-worker обрабатывает ошибки
Then 429 откладывается не менее чем на 7 секунд, а сетевой timeout переводит запись в `UNCERTAIN` и не вызывает слепую повторную отправку.

### AC-15: Отписка и удаление персональных данных (FR-20)
Given у пользователя активная подписка и очередь с неотправленным дайджестом
When он вызывает `/stop`, а затем `/delete_me`
Then будущих доставок нет, очередь отменена и его персональные данные удалены в пределах 24 часов при соблюдении обязательного retention.

### AC-16: MCP read-only изолирован (FR-21)
Given в ChatGPT подключён пользователь с ролью `analyst_readonly`
When он вызывает `list_active_listings`, `get_listing_evidence`, `get_source_health` или `preview_daily_digest`
Then получает только разрешённые нормализованные данные без секретов, а число внешних сетевых запросов и изменений БД равно нулю.

### AC-17: Изменяющий MCP требует владельца и подтверждения (FR-22)
Given не-владелец или владелец без `confirmed=true` вызывает `request_listing_recheck`
When gateway проверяет авторизацию и параметры
Then job не создаётся и возвращается структурированная ошибка 403/`CONFIRMATION_REQUIRED`.

### AC-18: Прозрачное состояние источников и аудит (FR-24)
Given тестовый scan упал из-за изменения структуры страницы
When owner читает `get_source_health` и журнал конкретного `run_id`
Then видит время последнего успеха, код сбоя, затронутый source, но не cookie/токены и не полный приватный HTML.

### AC-19: Независимые сигналы (FR-9)
Given два агрегатора воспроизводят одно и то же старое объявление и оригинальный источник недоступен
When вычисляется косвенная актуальность
Then зависимые копии учитываются как один сигнал, а статус остаётся `UNVERIFIED`.

### AC-20: Корректная остановка заблокированного бота (FR-19, FR-20)
Given подписчик заблокировал бота, и Telegram вернул соответствующий 403
When delivery-worker пытается отправить сообщение
Then подписка становится inactive, сообщение не повторяется, admin видит обезличенную причину.

### AC-21: Изоляция SSRF и secret leakage (FR-2, FR-21, FR-22, FR-23)
Given пользователь подал localhost/IP-literal/redirect на приватную сеть/вредоносный текст объявления
When интерфейсы принимают запрос и данные
Then сеть к запрещённым адресам не открывается, секреты не присутствуют в ответах, сторонний текст не становится инструкцией для MCP.

### AC-22: Повтор по команде ограничен (FR-4, FR-22)
Given owner 10 раз подряд запросил перепроверку одного listing ID
When система ставит задачи
Then создаётся не более одного активного задания для listing и остальные получают текущий `job_id`/`RATE_LIMITED`, при `DISABLED` источнике запрос не выполняется.

### AC-23: Не лицензированные фотографии не пересылаются (FR-15, FR-23)
Given источник разрешает публикацию ссылки и фактического резюме, но права на перепубликацию фото не подтверждены
When создаётся Telegram-сообщение
Then отправляются только собственный текст/цена/ссылка, без копирования и загрузки сторонних фотографий.

### AC-24: Обязательная проверка полноты извлечения (FR-6, FR-24)
Given тестовая разрешённая страница изменила вёрстку и парсер больше не нашёл цену
When сканирование завершает извлечение
Then карточка не проходит к публикации, `schema_drift` повышается, owner получает диагностическое событие; старая цена не подставляется как новая.

## Edge Cases

- EC-1: `403`, `401`, CAPTCHA или иная блокировка — автоматическая остановка данного режима; без proxy rotation/автоматического CAPTCHA solving.
- EC-2: `429` площадки — выдержать условия разрешённого API/сайта, не масштабировать параллелизм, зафиксировать health деградацию.
- EC-3: JSON вместо HTML или страница входа после редиректа — отличить от валидного пустого результата; не создавать события снятия.
- EC-4: Один объект на двух площадках с одинаковой площадью и домом, но другим этажом — не сливать; если тот же ID и новая цена — сохранить историю.
- EC-5: Карточка недоступна из-за сетевого тайм-аута — `STALE/UNVERIFIED`, не `REMOVED`.
- EC-6: «Под авансом», «забронировано» или «продано» — исключать из доступных даже при старой индексной копии.
- EC-7: Один и тот же отзыв/копия дублируется на разных агрегаторах — не считать независимыми подтверждениями.
- EC-8: Отсутствие точного адреса или спорное расположение внутри/вне полигона — отправить на проверку, не угадывать.
- EC-9: Прямое расстояние до станции не равно реальному пути через железнодорожные пути/автодороги — не оценивать пеший маршрут «по прямой».
- EC-10: Автоматическое геокодирование не удаётся или сторонний API достиг лимитов — кэш + `ROUTE_UNVERIFIED`, без бесконечных retries.
- EC-11: Резкое снижение цены в старом объявлении без прямого свежего сигнала — не отправлять как подтверждённое выгодное предложение.
- EC-12: Сеть Telegram оборвалась после отправки запроса, но до ответа — состояние `UNCERTAIN`, ручная сверка/пользовательский антиспам вместо слепого retry.
- EC-13: Telegram `429 retry_after`, `403 bot blocked`, миграция `chat_id` и недоступный Bot API — разные ветви обработчика ошибок.
- EC-14: Два экземпляра scheduler случайно работают одновременно — advisory lock или leader election, уникальные ключи заданий и outbox.
- EC-15: Неправильный UTC offset на летнем/зимнем времени — календарь хранит IANA timezone, а не постоянное UTC смещение.
- EC-16: Пользователь отписался между построением и отправкой дайджеста — worker повторно проверяет активность перед каждым вызовом Telegram.
- EC-17: База данных стала недоступна — прекращать публикацию, не продолжать на основе несохранённых in-memory данных.
- EC-18: Недопустимый URL из Telegram или MCP (ссылка на метаданные cloud, redirect на localhost) — отказ без network I/O.
- EC-19: HTML объявления содержит «ignore all instructions» — отображать как недоверенный текст, не исполнять и не пересылать как инструкции модели.
- EC-20: Отсутствие прав на источник либо отзыв разрешения после запуска — выключить адаптер, остановить jobs и выполнить необходимую политику удаления хранимых материалов.

## API Contracts

### Internal HTTP API (приватный, концептуальный v1)

Все внутренние endpoint доступны только доверенным процессам/админу по service auth. Swagger/OpenAPI 3.1 и точная error schema должны быть сформированы из типизированных моделей до начала реализации.

```ts
type UUID = string;
type ISODateTime = string; // UTC RFC3339

type Availability =
  | 'ACTIVE_DIRECT' | 'ACTIVE_INDIRECT' | 'UNVERIFIED'
  | 'STALE' | 'RESERVED' | 'REMOVED' | 'SOLD';

type SourceMode = 'LICENSED_API' | 'APPROVED_FEED' | 'PERMITTED_HTML'
  | 'USER_SUPPLIED' | 'DISABLED' | 'UNKNOWN_PERMISSION';

interface VerificationEvidence {
  id: UUID;
  listingId: UUID;
  sourceId: string;
  signal: 'ACTIVE' | 'INACTIVE' | 'RESERVED' | 'UNKNOWN';
  method: 'DIRECT_DETAIL' | 'OFFICIAL_FEED' | 'LICENSED_API'
    | 'CURRENT_SEARCH' | 'INDEPENDENT_REFERENCE' | 'USER_SUBMISSION';
  observedAt: ISODateTime;
  fetchedFrom?: string; // only allowed public URL
  independentClusterId?: string; // common copies share cluster
  permissionScope: string;
};

interface Listing {
  id: UUID;
  sourceRefs: { sourceId: string; externalId: string; publicUrl: string }[];
  priceRub?: number;
  areaM2?: number;
  rooms?: number;
  addressDisplay?: string;
  floor?: number;
  station?: 'LEVOBEREZHNAYA' | 'KHIMKI';
  transitMinutes?: number;
  transitMethod?: 'WALK_ROUTE' | 'PUBLIC_TRANSIT' | 'UNVERIFIED';
  availability: Availability;
  observedAt: ISODateTime;
  verificationAt?: ISODateTime;
  benefits: string[];
  riskFlags: string[];
};

interface ErrorResponse {
  error: {
    code: 'AUTHENTICATION_REQUIRED' | 'FORBIDDEN' | 'VALIDATION_ERROR'
      | 'NOT_FOUND' | 'SOURCE_NOT_ALLOWED' | 'RATE_LIMITED'
      | 'CONFIRMATION_REQUIRED' | 'CONFLICT' | 'DEPENDENCY_UNAVAILABLE';
    message: string;
    details?: Record<string, string>;
    requestId: UUID;
```

| GET | `/v1/listings/{id}/evidence` | analyst_readonly / owner | `200 {listing: Listing, evidence: VerificationEvidence[]}` | 401/403/404 |

`POST /v1/listings/{id}/rechecks` принимает `{ "confirmed": true, "reason": "manual_review", "idempotencyKey": "UUIDv4" }`. Этот запрос лишь добавляет job на разрешённый источник, не гарантирует результат. Подписки в MVP изменяет сам бот по верифицированному Telegram update, а не произвольный MCP клиент.

MCP определён в [`mcp/tools-manifest.json`](../mcp/tools-manifest.json). Вся авторизация и read/write-разделение дублируются на backend — аннотации MCP не являются security boundary.

### Telegram Bot API

- Команды: `/start` → показать условия и опциональный consent → создать подписку; `/settings` → обновить предпочтения; `/stop` → остановить; `/delete_me` → инициировать удаление; `/help`.
- Webhook: `X-Telegram-Bot-Api-Secret-Token` проверяется постоянным временем; уникальный `update_id` исключает повторную обработку. Альтернатива для личного маленького развёртывания: `getUpdates` long polling **без** webhook.
- Доставка: `sendMessage(chat_id, text, parse_mode='HTML', reply_markup=...)`; Telegram escaping всех внешних полей, ссылки из заранее нормализованного allowlist. Пользователь может заблокировать бота в любой момент.
- Формат уведомления: заголовок события/дата + стоимость, площадь, локация, статус/время проверки, станция/метод маршрута, достоинства, риски, кнопка «Открыть оригинал». При длинных дайджестах разбиение до лимита Telegram.

### Notification state machine

`PENDING -> LEASED -> SENT`; `LEASED -> RETRY_WAIT` only when безопасно определён факт неуспеха (например HTTP 429 или сетевое соединение не открыто); после возможной доставки при неизвестном результате `LEASED -> UNCERTAIN`; отписка вызывает `PENDING/RETRY_WAIT -> CANCELLED`; блокировка бота вызывает `BLOCKED` + inactive subscriber. После `UNCERTAIN` нет автоматической повторной отправки без явной согласованной стратегии сверки.

### Availability state machine

`UNVERIFIED -> ACTIVE_DIRECT/ACTIVE_INDIRECT` только по положительному допустимому сигналу; `ACTIVE_* -> STALE` по истечении TTL; `ACTIVE_* -> RESERVED/REMOVED/SOLD` только по явному отрицательному допустимому сигналу; `REMOVED -> ACTIVE_*` при новом подтверждённом событии возврата в продажу. Следить за конфликтующими источниками и хранить обе записи evidence.

## Out of Scope

- OS-1: обход антибот-защит, CAPTCHA, вход через чужие аккаунты, ротация прокси для преодоления ограничений и использование скрытых API без разрешения;
- OS-2: гарантия охвата «всех» объявлений на ЦИАН/Авито/Домклик без разрешённых каналов; реестр источников показывает объективные пробелы;
- OS-3: установление юридической чистоты квартиры/добросовестности продавца, получение закрытых реестров и автоматический контакт с продавцами;
- OS-4: перепубликация защищённых фотографий/полных описаний или персональных телефонов продавцов без соответствующих прав;
- OS-5: массовые сообщения Telegram-пользователям без `/start` и consent; произвольная рассылка через MCP;
- OS-6: покупка недвижимости, проведение переводов, кредитный скоринг, коммерческая реклама, монетизация подписок;
- OS-7: Telegram Mini App, карта-UI, мультигород, мультиязычность, персональные агенты для каждого подписчика в MVP;
- OS-8: автоматическая обработка ChatGPT в фоне без отдельного агентного backend/API; собственный ChatGPT MCP не заменяет scheduler;
- OS-9: платные/ограниченные API, self-host картографической платформы и постоянный AI inference до оценки необходимости и бюджета.
